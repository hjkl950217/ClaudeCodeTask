# cct GitHub Releases 发布流程

> 每次发布 cct 新版本走**tag 触发的自动发布**：写好发布文案（随仓库提交）→ 打 `v*` tag 推送 → `.github/workflows/release.yml` 自动跑测试、发布 PowerShell Gallery、创建 GitHub Release。全程不需要手动 `gh release create`，CI 也不做任何文案生成——正文就是仓库里的文档文件，只做机械读取粘贴。

## 一、发布参数表（本次 v0.2.0）

| 参数 | 值 | 来源 / 说明 |
| --- | --- | --- |
| 语义化版本 | `0.2.0` | `ClaudeCodeTask.UI/ClaudeCodeTask.UI.psd1` 的 `ModuleVersion`（内部唯一事实，PowerShell 要求不带 `v`） |
| Release 标题 / tag | `v0.2.0` | 对外一律带 `v`（标题 = tag = `v0.2.0`） |
| 发布文案文件 | `release-notes/v0.2.0.md` | **文件名 = tag**，CI 按 `release-notes/<tag>.md` 读取 |
| 改动区间 | `v0.1.0..HEAD` | 上一个 release tag 到当前 HEAD，用来归纳文案 |

**版本号规则**：psd1 `ModuleVersion` 永远不带 `v`（语义化，供 `release.yml` 校验更新）；对外标题、tag、正文一律用 `v0.2.0`。**文件名规则**：文案文件必须叫 `release-notes/<tag>.md`（含 `v`），CI 据此拼接路径，不做任何分支/生成。

**注意**：文案文件放仓库根 `release-notes/`（不随 tag 外变化）。不要放进 `docs/`——`.gitignore` 忽略整个 `docs/`（内部开发文档仅本地），进了 CI checkout 就找不到。

## 二、发布步骤（tag 自动触发）

### 1. 归纳改动（面向使用者，去技术化）

把区间内 commit 归纳成**使用者能看懂的价值**，不是内部实现名。参考 cc-switch（其 `docs/release-notes/`）等优秀仓库的写法：先一句导语讲「这版能给你什么」，再分「新功能 / 修复与优化 / 安装」小节；多用「你可以 / 现在能 / 不再需要」句式。内部实现词（命令路由、`includeFolderFind`、`TitleType`、`Add-Type`、枚举分层、`spinner` 等）一律换成人话或并入一句「内部重构」。纯文档类改动不单列。

### 2. 写发布文案并提交

把文案写入 `release-notes/v0.2.0.md`，第一行为标题 `# v0.2.0`，正文按上述结构。**文案文件必须与功能改动一起在 tag 指向的提交里**（先提交、后打 tag）。

````markdown
# v0.2.0

> <导语：一段话说清这一版的主要价值>

## 新功能

- **<能力>**：<一句话用户收益>

## 修复与优化

- <修复/改进一句话>

## 安装与使用

推荐从 PowerShell Gallery 安装：

```powershell
Install-Module -Name ClaudeCodeTask.UI -Scope CurrentUser
```

或下载本页 Assets 里的 **Source code** 解压，手动导入：

```powershell
Import-Module "<解压路径>\ClaudeCodeTask.UI\ClaudeCodeTask.UI.psm1" -Force
cct
```

更多用法见 `cct -h`。
````

### 3. 打 tag 并推送（触发自动发布）

```powershell
git push origin main
git tag v0.2.0
git push origin v0.2.0
```

推送 tag 后 `.github/workflows/release.yml` 自动执行三个 job：

| Job | 作用 | 失败影响 |
| --- | --- | --- |
| `test` | Pester 门禁 | 失败则不发布（后面 job 依赖它） |
| `publish-gallery` | 从 tag 改 psd1 版本 → 发布 PowerShell Gallery | 仅 PSGallery 不发 |
| `create-release` | 读 `release-notes/<tag>.md` 建 GitHub Release（标题 = tag，正文 = 文档内容） | 仅不建 release |

`publish-gallery` 与 `create-release` 互不依赖、并行；Release 的 Source code 源码包由 GitHub 对 tag 自动生成，无需上传附件。

### 4. 发布后检查

- GitHub Actions 页确认 `test` 绿、`publish-gallery` 与 `create-release` 均成功（约 2–3 分钟）。
- PowerShell Gallery 确认 `ClaudeCodeTask.UI` 出现新版本。
- Release 页确认标题 = `v0.2.0`、正文与文案文件一致、Source code 附件可下载。

## 三、为什么 CI 不含任何「生成」

发布正文来自 `release-notes/<tag>.md` 文件，由作者在打 tag 前写好并随提交入库（可审阅、有 git 历史）。CI 的 `create-release` job 只做一件事：`body_path` 指向该文件，`softprops/action-gh-release` 原样上传。文案怎么归纳、怎么写，全发生在仓库内、发布之前；不在 action 里做大模型调用、commit 总结或文本拼接。
